# 踏んだ罠と対処

[English](lessons.md) · [fpga-mac に戻る](../README_ja.md)

[fpga-pynq-z1](https://github.com/tsjshg/fpga-pynq-z1)（PYNQ-Z1 で三値の LLM を動かしたプロジェクト）で実際に踏んだものを、どのボードの回路でも役立つ形にまとめ直しました。数字は、断りが無いかぎり PYNQ-Z1（XC7Z020 -1）での実測値です。

**特に繰り返したもの**は次の3つです。

1. データの段数と有効ビットの段数のずれ
2. 測定式の固定費を帯域の目減りと読み違えること
3. 比較相手の CPU 実装を雑に作ること

## Docker の中の Vivado（macOS）

- **`LD_PRELOAD` が要る。** Rosetta の下では、`libudev`・`libselinux`・`libz`・`libgdk-x11` を先に読み込ませておかないと Vivado が落ちます。`vivado.sh` が毎回設定しています。
- **`launch_runs -jobs 2` にする。** Vivado は IP ごとに 1 本あたり約 2.8 GB のプロセスを立てます。`-jobs 8` ではコンテナのメモリ（Docker に 15 GB 割り当て）を超えて OOM killer に殺されました。
- **`bd` と `all` の2段にして、必ず `bd` を先に通す。** ブロックデザインの検証だけなら 30 秒〜1 分で終わります。いきなり合成まで回すと、配線の誤りに気づくまで数分かかります。
- **Vivado のフォルダは内蔵ディスクに置く。** bind mount で見せるので、UNIX の権限を持てないファイルシステム（exFAT など）では問題が出ます。Docker 自体のディスクイメージは外付けでも動いています。その場合は、外付けがマウントされていることを確かめてから Docker を起動してください。
- **`open_run` の後は `get_property STATS.*` が空になる。** 警告が出るだけで値は返りません。WNS は `open_run` の前に読み、資源は `report_utilization -file` の出力から拾います。これに気づかず、DSP の数を見落としかけました。

## Tcl とブロックデザイン

- **ボードファイルが無いボードは、部品番号と PS の明示設定で作る。** PYNQ-Z1 は Digilent にも PYNQ にもボードファイルがありません。PYNQ 公式の `base.tcl` の PS7 設定（533 項目）をそのまま使うのが正解でした。
- **流用した PS 設定は、使わない AXI ポートが開いたまま残る。** 使わないポートは明示的に閉じないと、「クロック未接続」で `validate_bd_design` に落ちます。
- **`apply_bd_automation` は AXI のインタフェースしか配線しない。** ストリームだけでつないだセルは、クロックとリセットを自分で結びます。`proc_sys_reset` のセル名は自動で付くので、名前を決め打ちせず VLNV（`*:proc_sys_reset:*`）で探します。
- **Tcl のブレース `{}` の中では変数が展開されない。** `-config {… intc_ip $smc …}` は、文字列 `$smc` がそのまま渡って失敗します。変数を埋める行だけ二重引用符で組みます。
- **自作モジュールのポートには `X_INTERFACE_INFO` を明示する。** 名前からの推論に任せると、IPI がストリームのインタフェースとして束ねてくれないことがあります。
- **何も使わないストリームの終点には `DONT_TOUCH` のレジスタを1個置く。** 置かないと、合成器が「使われていない」として TDATA を配線ごと消し、データが本当に流れているのか確かめられなくなります。

## クロックとタイミング（XC7Z020 -1）

- **FCLK は要求どおりには出ない。** 150 MHz を頼むと、IO PLL の 1000 MHz を 7 で割った 142.857 MHz になります。帯域の計算には `PCW_ACT_FPGA0_PERIPHERAL_FREQMHZ` を読み戻した値を使います。
- **AXI DMA と SmartConnect の組み合わせは 200 MHz が通らない**（WNS −0.77 ns）。142.86 MHz なら余裕がありました。
- **142.86 MHz で落ちたら、まず AXI DMA の中を疑う。** 最悪経路は毎回のように S2MM の転送長カウンタ（`c_sg_length_width` ビットの桁上げ）でした。同じ経路でも、置き場所の運で 0.37 ns 開くことがあります。手当ては次の3つです。
  1. `c_sg_length_width` を縮める（23 ビットなら1回の転送は 8 MiB 以下）
  2. 自作回路の大きな扇形を減らして、混雑を下げる
  3. 125 MHz に下げる。HP 2本・125 MHz の道幅 2.000 GB/s は DDR の壁（実測 2.009）とほぼ同じなので、帯域で律速される回路なら下げても損がない
- **1 サイクルに重い処理を2つ並べない。** 142.86 MHz では 7.00 ns しかなく、通せるのは実質「小さい演算ひとつ」です。実際に落ちた例:
  - 分散 RAM の読み出しと掛け算（−0.502 ns）
  - ビート位置による 192 個のアドレス解読（−0.480 ns）
  - 32 bit 加算・シフト・比較・BRAM 書き込み（−0.134 ns）

  面積は余っているので、最初から段を余分に刻んでおきます。
- **小さい掛け算は放っておくと DSP に載らない。** 8×8 は LUT で組まれ、CARRY4 が 4 段つながりました。積のレジスタに `(* use_dsp = "yes" *)` を付けると、DSP 10 個で WNS が −0.502 から +0.062 ns になりました。
- **数千個のレジスタの CE を1本の信号で駆動しない。** 論理 0 段なのに、遅延の 93%（6.3 ns）が配線でした。`(* max_fanout = 64 *)` を付けて複製させます。一括クリアも同じで、1 段遅らせて構いません。自分の経路は通っていても、混雑で他所（DMA）を落とすことがあります。
- **可変の添字での読み書きは配線を爆発させる。** `acc[b*8+i] <= acc[b*8+i] + x` は、b が 192 個のアドレス解読に扇形に広がりました。b が順に回るだけなら、アドレスで選ばずに累算器の側を回します（添字が全部定数になる）。複雑さは遅くてよい経路（結果の読み出し）に寄せます。
- **合成結果は思い込みでなくレポートで確かめる。** 「深くすると分散 RAM が膨らむ」と身構えたら、登録つき読み出しなので最初から BRAM に載っていた、ということがありました。DSP 0 個も、レポートを読むまで気づきませんでした。

## RTL の正しさ

- **【最も繰り返した誤り】データの段数と有効ビットの段数を数え合わせる。** データが 3 段、有効ビットが 4 段で、ビート b の積がビート b−1 の累算器に入っていました。合計は保存されるので「全部足す」系の検査は通り、個々の値だけが1つずれます。生成スクリプトの段数の数え間違いでも、同じ形の誤りが出ました。
- **出力レジスタは「空いているか、下流が受け取ったとき」だけ載せ替える**（`load = !m_tvalid || m_tready`）。無条件に載せ替えると、背圧でビートを落とします。FIFO が深いと実機では表に出ないので、xsim で背圧をかけないと見えません。
- **TLAST は、最後が半端でも必ず出口まで運ぶ。** 区切りだけで結果を吐く作りにすると、端数のある転送で TLAST が届かず、DMA が永久に終わりません。
- **パイプラインが抜けきる前に結果を読まない。** 出力用の状態へ直接移ると、先頭の数個が未完成の累算器を読みます。排出用の状態を数サイクル挟みます。
- **実機の前に xsim で通す。** tvalid の欠落と tready の背圧を混ぜ、長さ 1 の列などの端も踏みます。xsim を通さずに実機で3回誤診して、丸一日を使ったことがあります。xsim で先に照合した版は一発で通りました。**論理の誤りはシミュレータで、タイミングと帯域だけを実機で**確かめます。
- **期待値は回路と別の書き方で作る。** numpy やテストベンチの単純な足し算で作ります。照合は全部の語に対して行います（総和だけでは段ずれを見逃します）。
- **大きな加算木や繰り返しの多い回路は、スクリプトで生成する。** 40 項の木を手で書くと必ず間違えます。生成された `.v` は直接編集しません。
- **壊れ方が分からないときは、入力を系統的に振って対応表を作る。** 値を睨んでも分からなかったものが、「入力のビート b を変えると出力のどこが動くか」を8通り試したら、すぐに一様な −1 だと分かりました。

## DMA・HP ポート・帯域

- **AXI ストリームは1本あたり「幅 × FCLK」が上限。** 64 bit・100 MHz なら 0.80 GB/s です。最初のループバック測定を「DDR の 74%」と読んだのは誤りで、実際は読み書きそれぞれが自分の道幅の 96% に張り付いていただけでした。
- **DDR を使い切るには HP ポートを2本使う。** HP0 と HP2 を選びます（HP0/HP1、HP2/HP3 は PS 側で対になっていて、入口で先に詰まる）。PYNQ-Z1 では HP0 だけで 1.143 GB/s（道幅の 100%）、HP0 + HP2 で 2.009 GB/s（DDR の理論値の 96%）でした。CPU 2 コアの逐次読み出しは理論値の 33% しか出ません。
- **帯域は「1 回の時間で割る」のではなく「傾き」で測る。** PYNQ の `transfer`/`wait` には、1 チャネル対あたり約 0.7〜0.8 ms の固定費があります。全量と半量を測って差で割ると、固定費が消えます。これを知らずに、「道幅の 98.7%」と書いたものが本当は 100.0% でした。**数字が合わないときは、回路を疑う前に測定式を疑います。**
- **2本に分けるときは、順序の依存を壊さない分け方をする。** バッファ単位でポートに振ると、後ろの層を先に流すことになって嘘になります。各組の行を半分ずつ振り分ければ、順序は保たれます。
- **単純転送モードの DMA は、一度も転送していないと Idle が立たない。** RS=1 にしただけの状態で Idle を待つと、永久に待ちます。

## PYNQ（ボード上の Python）

- **root かつログインシェルで動かす。** 理由は2つです。
  - ビットストリームの書き込みに root が要る
  - PYNQ の venv と `XILINX_XRT` は `/etc/profile.d` で設定されるので、ログインシェルでないと入らない

  `sudo bash -lc "…"` で起動し直します（ひな形の `run.sh`）。
- **ビットストリームは `.bit` と `.hwh` を同じ basename で並べて置き、`Overlay()` で読む。** JTAG は要りません。
- **小さい転送を何度もするなら、PYNQ の API を使わない。**
  - `transfer`/`wait` は 1 回 724 µs かかり、レジスタを直接叩くと 321 µs で済みました。半分以上が Python の処理です。
  - numpy 経由の MMIO は、読み書き 1 回あたり 6〜14 µs かかります。
  - DMA の起動・待ち・コピーを C に移したら、1 トークンが 177 ms から 126 ms になりました。
- **転送の回数そのものが律速になる。** 回路は道幅の 100% で動いているのに、1 トークン 181 回の転送の固定費が時間の 83% を食っていました。ストリームに見出し（行数・行の長さ）を付けて、1 回の転送で多くの仕事を流す形に変えたら消えました。**回路の速さより、回路への渡し方のほうが効く領域があります。**
- **`PynqBuffer` を毎回スライスしない。** スライスのたびに Python の `__array_finalize__` が走り、1 回 100 µs かかります。最初に `.view(np.ndarray)` で素の配列にしておきます。`ndarray.ctypes.data` も 1 回 37 µs かかるので、アドレスは最初に1回だけ取ります。
- **CMA は表示を当てにせず、実際に allocate して測る。**
  - `cma=256M` で `CmaFree` が 233 MB と出ていても、実際に取れた合計は 176〜208 MB で、測るたびに揺れました。
  - 1 回で取れたのは 160 MB までで、16 MB ずつなら 192 MB 取れました。
  - 原因は断片化です。先に `drop_caches` をすると少し良くなります。
  - 逆に、`CmaFree` が小さく見えても、Overlay を読み直すと DRM の保持分が解放されて取れたこともあります。
- **ボード上の numpy で巨大な配列をうっかり作らない。** RAM は 491 MB しかありません。`rng.integers(-1, 2, size=(262139, 640))` は、dtype を指定しないと int64 で 1.25 GB になって落ちました。

## ボードの運用

- **PYNQ-Z1 は起動ごとに MAC アドレスがランダムになる。** そのため固定 IP が必須です。`interfaces.d/` に `.bak` を置くと二重に適用されます。
- **`sudoers.d` のファイル名にドットを含めると無視される。** 権限は `0440` にします。
- **シリアルは、AC アダプタで給電しているときは使えない。** Mac に USB でつないで給電するか、`/boot`（FAT）を Mac で直すことを退路にします。起動に関わる変更は、退路を確保してから行います。
- **CMA の大きさは `/boot/uEnv.txt` の1行で変えられる。** デバイスツリーではなくカーネルの既定値で決まっているからです。bootargs は手で打たず、`/proc/device-tree/chosen/bootargs` から作ります。

## 測り方と比べ方

- **数字には「実測」か「試算」かを書く。** 別々に測ったものを足した値は試算です。
- **比較相手の CPU 実装も、自作の回路と同じだけ本気で作る。** CPU の attention を `-O2`（NEON 無効）で焼いていて、83 ms と出ていました。`-O3 -mfpu=neon` を足すだけで 47 ms です。それまでの「CPU の何倍」は、すべて 1.8 倍ほど過大でした。**作ったものは丁寧に測り、比べる相手は雑に測る、という偏りが2回続きました。**
- **Mac とボードで浮動小数点の結果をビット単位で揃えるなら、焼き方と演算を固定する。**
  - `-ffp-contract=off` を付ける。clang は既定で FMA に融合します。
  - fast-math は使わない。
  - 和の順序を固定する。
  - `expf`・`rintf` は libm によって最下位ビットが違うことがあるので、自前で書く。
  - AArch64 で融合演算になる `vrecpsq_f32` は使わない。

  これで ARMv7 のボードと Apple Silicon で、ビット単位で一致しました。
